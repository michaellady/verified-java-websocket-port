## 6. PRD metadata sections — full text

### goal

Codify a repeatable, evidence-backed Java-to-Rust porting method and publish it as a portable Claude Code and Codex skill after it succeeds on complete, materially different open-source laboratories.

### successCriteria

Laboratory Zero first proves the complete secure, replayable evidence and cutover lifecycle. Java-WebSocket and CommonMark then complete all semantic, mutation, formal, security, material-memory, per-workload performance, protected-evaluation, and production-shaped cutover-rehearsal gates; contamination-safe baseline-vs-skill evaluation shows measurable uplift in fresh Claude Code and Codex agents; assurance cases survive independent replay; and port-java-to-rust v1 publishes with claim-scoped, freshness-aware evidence. JSON Schema and Netty HTTP/2 then harden the method without weakening historical claims. The skill can guide a user toward a target-specific CUTOVER_READY decision but never confers that claim without evidence from the declared integration boundary and production-shaped environment.

### nonGoals

- Do not mechanically formalize or prove every Java implementation detail before Rust work begins
- Do not claim an abstract TLA+ or other model proves shipped Java or Rust without a stated trace, refinement, bounded-check, or deductive connection
- Do not preserve undocumented Java quirks when a declared standard or neutral suite has higher oracle priority
- Do not use first-party unsafe Rust; dependency unsafe remains a reviewed trusted-computing-base boundary
- Do not claim to port all of Netty; laboratory 4 is an honestly scoped complete HTTP/2 codec-subsystem port
- Do not require TLS/WSS, RFC 7692 compression, proxies, reconnect, Android, or Java API parity in the initial WebSocket laboratory
- Do not publish the skill after only WebSocket or before clean cross-runtime held-out forward tests
- Do not add helper code to the skill for judgment that belongs in instructions or that fails the Primitive Test
- Do not treat compilation, translated line count, main-branch merge, a green aggregate command, LSP diagnostics, model agreement, or document completeness as evidence of behavioral completeness
- Do not build a generic language-neutral porting protocol in v1; the protocol and evidence model remain intentionally Java-to-Rust-specific
- Do not claim Java API parity unless a child PRD explicitly selects it as the replacement boundary
- Do not claim CUTOVER_READY from public laboratory evidence alone; production readiness is bound to the user's actual declared boundary and production-shaped environment
- Do not operate or mutate a user's live production environment without separate explicit authorization
- Do not assume Rust saves memory; every laboratory must demonstrate its predeclared material memory hypothesis on representative workloads
- Do not remove the Java executable or rollback path before an explicit independently attested removal decision
- Do not copy or closely adapt third-party code, prose, tests, or datasets without pinned provenance, license review, attribution, contamination analysis, and required notices

### dataModel

The Java-to-Rust evidence protocol uses canonical, semantically versioned, content-addressed schemas for Laboratory, SourcePin, SurfaceItem, SemanticId, MigrationMap, PortSeamDossier, BehaviorDelta, CompatibilitySurface, CutoverContract, Oracle, Corpus, SemanticEvent, Trace, Divergence, Claim, ClaimReplayBundle, Model, ProofObligation, EvidenceRun, MutationResult, BenchmarkRun, DeveloperToolRun, ResourceClaim, PerformanceEnvelope, Review, SkillRevision, ForwardTest, ProgramSnapshotManifest, FailureEnvelope, Attempt, GeneralizationDecision, AuthorizationAction, ArtifactClassification, and StalenessEdge. Java and Rust compiler/LSP semantic IDs, specifications, observations, proof obligations, corpus vectors, production code, independent reruns, cutover evidence, and skill revisions remain distinct but explicitly linked. Historical schemas and validators are retained; migration produces new derived artifacts and never rewrites prior bytes.

### authModel

The frozen foundation policy defaults to distinct short-lived workload identities and four artifact-scoped action roles: method/schema steward, port implementer, oracle/held-out custodian, and release attestor. A child may use a program-owned, digest-bound single-owner amendment only when the sole owner explicitly decides it; every resulting claim is labeled owner-attested rather than independent. In either mode, every sensitive action binds canonical artifact, vulnerability-disposition, policy/amendment, identity, role, timestamp, expiry, sandbox, publication, and nonce fields; replay, cross-company access, over-scoped actions, post-review mutation, or revoked authority is denied and logged. Knowing a protected digest grants no access.

### architectureNotes

Use a small Java-to-Rust-specific protocol kernel with explicit laboratory, oracle, tool, LSP, sandbox-runtime, and platform adapters. The flow is hostile static intake, sandboxed authoritative Java build and retained oracle, semantic-ID migration map and Port Seam Dossier, idiomatic safe Rust vertical slices, language-independent public/hidden/sealed corpora, layered trace-backed formalization, claim-linked replay evidence, independent evaluation, Program Snapshot acceptance, fail-closed release firewall, and production-shaped shadow/canary/rollback rehearsal. Docker sbx is the first verified macOS sandbox-runtime profile, not a portable requirement baked into the skill core; later hosts must provide the same capability contract or remain blocked. The immutable evidence DAG spans Git-managed schemas and small fixtures, immutable public evidence blobs, and a separately protected held-out store. Project projections, dashboards, badges, and indexes are rebuildable. Each lab is a whole replacement behind an explicitly declared boundary; parity and refinement stay separate; every Java/Rust/spec disagreement enters the Behavior Delta Ledger; Java remains executable until all gates and an explicit removal decision pass.
