# F002 — A backpressure fixture that assumes a resource's size instead of driving it to refusal is host-specific
phase: adapter tests (nearest: port-link / port-calibrate)   step: n/a   date: 2026-09-02T04:30Z
what happened: `stalled_peer_reader_trips_the_bounded_write_deadline` sent a fixed 48 x 64 KiB flood sized against macOS loopback buffers of about 128 KiB each way. Linux autotunes the send buffer to `tcp_wmem[2]` (4 MiB) and absorbed 4.05 MiB under the adapter's write pattern, so the write never stalled, the client idled on read timeouts, and the peer's 60 s hold ended in `SocketError("ConnectionReset")`. Feeding more was not enough on its own: the core's `max_frames` and `max_actions` budgets (64 each) stopped output at 4.0 MiB, about 50 KiB short of the kernel, and every later command became a silently dropped `Rejected` disposition.
what it cost: `make -C rust gates` could not go green on Linux; about two hours including a first fix that fed more without raising the budgets.
where the deciding moment was: when the fixture chose a flood size. The expectation was computed from a host property (REFERENCE section 4, first form, in its host variant) and the receipt recorded Linux legs only inside Docker linuxkit VMs whose buffers happened to be small.
evidence: `rust/ws-testee/tests/loopback.rs` comment block; commit f345371; kernel probes recorded in `.claude/CLOUD-ENVIRONMENT.md`.
bin: NEW RULE candidate — a backpressure fixture drives the resource to refusal and lets the kernel decide when; it never encodes a buffer size, and the core's own budgets must be raised above any plausible kernel cap. Not yet filed against the family.
