# F006 — I reported a vendored document as "unbound" when it was bound to the plane it came from
phase: criteria audit / US-023 formal coverage   step: n/a   date: 2026-09-02T22:28Z

what happened: the `us023-formal-coverage` track reported, and I verified and landed in `92556bd`, that the 24-obligation catalog `assurance/formal/obligation-catalog.json` "is unbound on BOTH sides" — 0 of 24 Rust `source_path` values existing, namespaces `websocket_core`/`websocket_driver` naming no shipped crate, and four of five `denominator_basis` pins drifted with one naming a file that "exists in no tree." I checked each of those against the Claude-plane working tree, found them true, and wrote them up as defects in the catalog. **Two of the three are wrong.** The catalog is vendored byte-identically from `origin/codex/race-catchup`, and read against THAT plane: all 4 distinct Rust `source_path` values exist there; the Codex plane ships crates named `connection-core`, `websocket-driver` and `websocket-testee`, which is exactly what the namespaces name; and 4 of the 5 `denominator_basis` pins match the Codex plane's CURRENT files byte-for-byte, the fifth matching a Codex commit (`89ecf1e`) the plane has since moved past. `corpora/frame/codec.json` "exists in no tree" only because it exists on the Codex plane, which is read-only from here — its creating commits (`5307535`, `8e5b19b`) are reachable from `origin/codex/race-catchup` and from nothing else.

what survives: the **Java column finding stands, and is now sharper for being isolated.** Its 15 distinct `source_path` values are synthesised paths treating a METHOD as a file (`upstream-java/org/java_websocket/WebSocketAdapter/onWebsocketPing.java`), and they exist on NO plane — not Claude's, not Codex's. All 24 share ONE `source_sha256`, the whole-archive digest, and all 24 read `connection_state: DISCONNECTED`. That is a real defect and it is plane-independent.

what it cost: a landed commit message and two board rows asserting that master US-008's denominator "binds nothing" and that "any coverage number computed against it measures a document that binds nothing." That is false as written and it is the more damaging direction of error — it indicts the Codex plane's work for a mismatch created by reading its document against someone else's tree.

where the deciding moment was: when I checked "does this path exist?" against the working tree and stopped there. The catalog announces its own provenance — the track that vendored it asserted its sha256 AND its git blob id against `origin/codex/race-catchup`, and I verified that myself in the `66cefbd` landing. Having established that the document came from another plane, the only correct test of its bindings is against that plane. I ran the natural test instead of the right one, got a clean and dramatic answer, and did not ask what the answer meant.

evidence: `git cat-file -e origin/codex/race-catchup:<path>` for each of the 4 Rust paths (all present) and each of the 15 Java paths (all absent); `git ls-tree origin/codex/race-catchup:rust/` listing `connection-core`, `websocket-driver`, `websocket-testee`; a recomputation of all five `denominator_basis` pins against `origin/codex/race-catchup` (4 MATCH, 1 differs); `git for-each-ref --contains` showing `5307535`, `8e5b19b` and `89ecf1e` reachable only from `origin/codex/race-catchup`.

Every other input in the report still matches. The `basis_pin_drift corpora/frame/codec.json … on_disk=READ_FAILED` line that misled me is a FIELD INSIDE the report's own output, not the cause of the failure, and the refutation was available in the same test run: `TestRetainedReconciliationIsExactlyWhatTheDenominatorsDerive`, the only test that reads that pin, PASSED while the report test failed. Filed as F008, "the most recent explanation standing in for the diagnosis" — I attached a failure to the most salient recent finding instead of reading the failure. That is the same root as this finding's own class: running a check, or an explanation, without first pinning what it is about.

bin: a NEW class for this program's collection, and a close relative of the one it keeps finding. The recurring defect is **existence standing in for identity** — a name or a presence accepted where content should be bound. This is its mirror image: **absence standing in for defect** — a lookup that fails against the wrong subject, read as proof the subject is broken. Both come from the same root, which is running a check without first pinning what it is a check ON. The portable rule: before concluding that a document's references are unbound, establish which tree the document is ABOUT, and test against that tree. A vendored artifact is about its origin until something rebinds it.

what this changes for the owner: not "repair the catalog's pins" — they are correct where they point. The real question is whether a Codex-plane catalog can serve as the Claude plane's denominator at all. Master US-008 counts 24 obligations from this document; measuring the Claude plane against it needs a plane-crossing correspondence (Codex `connection-core` to Claude `ws-core`, and so on) that nobody has established and that is an owner decision, not an inference. It is also precisely the "name-normalising rule" the deferred `catalog-rust-column` track was told NOT to invent — and that instruction is now better founded than when I wrote it: the mapping is not a shortcut to avoid, it is a real decision to escalate.
